用户指出阶段二十四仍不符合宠物作为主要入口的要求：自由截图等模式必须在宠物上直接启动，不能先打开设置再点操作。此次保留管理页面，将四种截图模式直接集成到工具分支，共用截图调度、隐藏与恢复链路；截图成功后才打开批注，取消/失败返回宠物，原先已打开的管理窗口恢复原页。会议计时也加入直接开始/暂停/继续操作，已有工作计时、清理确认继续直接执行。历史二十四修复仍有效，但不作为快捷截图需求的完成证据。

原因是上一轮把快捷操作理解为页面导航；回归也围绕“打开设置第8页”，没有按“宠物按钮直接进入相应截图模式”验收。此轮新增Action::Capture(Mode)，由监视器直接进入CaptureFlow，不交给Settings::open_from_pet；四个按钮传递明确模式。收起菜单并等待200ms绘制更新后复用现有ScreenshotService，单任务保护，隐藏贴图和已打开的工作台，避免截到自己的工具菜单。截图生成代次变化才打开批注；Esc取消/错误不弹空的管理页，原预览保留，先前已打开工作台只恢复可见性而不抢焦点/还原最小化。截图状态在宠物卡内可查看，配置齿轮保留管理入口。

会议卡直接开始/暂停/继续/结束计时；状态变化调用既有MeetingService，不自动查询麦克风、录音或打开会议页。工作计时及清理执行前确认维持原直接交互。涉及文字输入/历史查看的便签、待办、剪贴板与报告仍使用相应编辑/列表页面，此轮没有增加独立宠物编辑器或历史浏览器。

## 原因与证据

截图已有代码连接：宠物 Tools 分类输出 Screenshot，监视器路由到设置第8页；不是截图只有设置侧栏入口。不过截图按钮藏在设置卡内，发现性差。

所有工具的 open 方法原先只设置 tab 和 open=true。设置窗口最小化时仍存在且 open=true，因此只是换页面，窗口继续藏在任务栏。当前普通实例PID42360的只读探针 `evidence/pet-tools-stage24-before.json` 显示 settings.minimized=true，窗口位置[-32000,-32000,-31840,-31972]。旧版本再次接收 --settings 请求后，`evidence/pet-tools-stage24-old-open.json` 仍显示 minimized=true。

确定性失败用例 `opening_screenshot_restores_a_minimized_workbench_once` 修前在 Minimized(false) 指令断言失败，修后通过。原测试只测部分卡片动作，没有点击截图，也没有最小化→重新打开场景；仅证明 Action 存在不足以证明可见页面打开。

这解释一种已证实的“点击后没打开”情况，不把它称作所有悬停、点击问题的唯一原因。

## 改动

- Settings::reveal 记录一次性显示请求，实际设置 viewport 发送 Visible(true)、Minimized(false)、Focus；后续渲染不重复抢焦点。
- 宠物页面跳转统一由 Settings::open_from_pet 分发；截图、报告、计时、便签、待办、会议、剪贴板、清理中心及设置都走真实页面。
- 托盘、右键、悬浮工具栏和 --settings 复用 reveal；截图结束回页使用原有 open_screenshot，保留截图隐藏/恢复流程。
- 工具分类维持520×460包络，截图独立为“屏幕工具”卡，不再混在设置卡内。报告、屏幕、设置三卡仍顺序展开且动画期间禁用工作操作。
- 打开入口不会自动截图、采集报告、清理系统或启用剪贴板；未实现的录音等没有加入入口。
